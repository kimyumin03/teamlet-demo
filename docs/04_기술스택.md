## 1. 핵심 결정 상세

### 1-1. Next.js App Router (RSC 기반)

**왜**:
- HR 도메인은 **폼 + 결재 + 권한 체크**가 대부분. Server Components + Server Actions로 자연스럽게 처리
- "정보 변경 모달" → Server Action으로 트랜잭션 처리 + 결재선 라우팅이 깔끔
- SEO는 필요 없지만 SSR로 초기 진입 빠름 (대시보드 한눈에)

**Pages Router 안 쓰는 이유**: 폼 도메인에서 GetServerSideProps의 보일러플레이트가 무거움

**라우팅 컨벤션**:
```
/app
  /(auth)/login, /signup, /join-company        ← 로그인 전
  /(app)/...                                    ← 로그인 후, 사이드바 레이아웃
  /(app)/company/[companyId]/...                ← 회사 컨텍스트 (멀티 테넌시)
  /(admin)/...                                  ← 시스템 관리자 (B2B 세일즈)
  /api/...                                      ← Route Handlers (외부 호출/Webhook)
```

### 1-2. Tailwind v4 + shadcn/ui (Flex 색감 회피의 핵심)

**왜**:
- shadcn은 **컴포넌트를 소스로 복사**해서 우리가 직접 커스터마이즈. 라이브러리에 종속 X
- Tailwind v4의 `@theme` 토큰 시스템 = 디자인 시스템 한곳 관리
- Flex의 초록→청록 그라데이션을 **절대 안 쓰도록** 토큰 자체에서 제거

**금지 사항** (디자인 시스템 문서로 강제):
- `from-green-* to-cyan-*` 같은 그라데이션 클래스
- Flex 시그니처 컬러 (#22c55e 류 비비드 그린 단독 사용)
- 둥근 정사각형 아이콘 컨테이너 (Flex 시각적 시그니처)

**대신**:
- 우리만의 Primary 컬러 팔레트 (디자인 시스템 문서에서 확정)
- 컬러 토큰: `--color-primary`, `--color-accent`, `--color-success`, `--color-warning`, `--color-destructive` 등
- "다른 웹처럼 보여야 함" = Notion/Linear/Vercel 톤의 절제된 미니멀

### 1-3. Prisma + Kysely 조합

**왜**:
- **Prisma**: 스키마 정의, 마이그레이션, 일반 CRUD (생산성 최고)
- **Kysely**: 복잡한 쿼리 (시점 기반 조회, 권한 scope 적용, 검색 인덱스 활용)

**Prisma 단독으로 부족한 곳**:
- 시점 기반 조회 (`PositionHistory` "X월 X일 시점" 쿼리는 윈도우 함수 필요)
- 검색 (`pg_trgm` 유사도 정렬, `<%` 연산자)
- 동적 권한 scope 필터 (런타임에 조건 조합)

**합의**:
- 스키마는 한 곳 (`schema.prisma`) — Kysely도 같은 스키마 참조 (`prisma-kysely` 플러그인)
- 일반 페이지의 90% = Prisma
- 검색 / 시점 조회 / 권한 평가 = Kysely

### 1-4. 권한 평가 자체 구현 (CASL/Oso 안 쓰는 이유)

**왜 라이브러리 안 씀**:
- 우리 모델 = RBAC + Scope + 동적 역할 (조직장) + EffectivePermission 캐시
- 라이브러리들은 표준 RBAC/ABAC 가정. 우리 캐시 모델·동적 역할이 어색하게 들어감
- 권한이 도메인 핵심 → 직접 구현이 가독성·디버깅 면에서 우위

**구조** (디렉토리는 아래 폴더 구조에 명시):
```
/modules/auth
  /permission
    catalog.ts          ← 70개 권한 정의 (시드)
    evaluator.ts        ← 권한 평가 엔진
    scope.ts            ← scope 적용 (전체/부서/직속/본인)
    cache.ts            ← EffectivePermission 캐시 invalidation
```

### 1-5. AxHub Adapter (수기 ↔ API 무중단 전환)

**핵심**:
모든 외부 의존성은 **인터페이스**로 추상화. 수기 구현체 → 나중에 AxHub 구현체로 갈아끼우기.

```
/modules/integrations/axhub
  /contracts             ← 인터페이스 정의 (수기/API 공통)
    IIdentityProvider.ts
    INotificationGateway.ts
    IFileStorage.ts
    IEmployeeDirectory.ts ★ 신규
    IOrgDirectory.ts
  /manual                ← 현재 (수기 입력) 구현체
    ManualIdentityProvider.ts
    LocalFileStorage.ts
    ManualEmployeeDirectory.ts ★ — CSV 임포트 처리
  /axhub                 ← 나중에 추가될 AxHub API 구현체 (자리만)
    AxHubIdentityProvider.ts.stub
    AxHubEmployeeDirectory.ts.stub ★
  index.ts               ← 환경변수로 어떤 구현체를 쓸지 선택
```

#### IEmployeeDirectory 계약 (수기/API 공통)

```ts
interface IEmployeeDirectory {
  // ── 단건 (수기·API 공통, 즉시 처리)
  getEmployee(companyId: string, id: string): Promise<Employee | null>
  findByExternalId(companyId: string, externalId: string): Promise<Employee | null>
  createEmployee(input: CreateEmployeeInput): Promise<Employee>
  updateEmployee(id: string, input: UpdateEmployeeInput): Promise<Employee>

  // ── 벌크 (MVP=CSV, 연동 후=API)
  // 같은 시그니처. ManualEmployeeDirectory는 CSV 파싱,
  // AxHubEmployeeDirectory는 AxHub API 페이지네이션 fetch.
  bulkSync(input: BulkSyncInput): Promise<BulkOperation>

  // ── 변경 감지 (API 모드 전용)
  // ManualEmployeeDirectory는 no-op 반환 → 호출 측은 동일 코드 유지
  subscribeToChanges?(handler: ChangeHandler): Unsubscribe
}

type BulkSyncInput = {
  companyId: string
  operationType: BulkOperationType
  initiatorUserId: string | null  // null = system (스케줄러/Webhook)
  source: 
    | { kind: 'csv'; fileUrl: string }
    | { kind: 'axhub_api'; cursor?: string; scope?: AxHubScope }
  conflictStrategy: 'manual_review' | 'axhub_wins' | 'hr_wins'
  dryRun: boolean  // true = 검증만, false = 실제 적용
}
```

#### 처리 파이프라인 (공통)

수기 CSV와 AxHub API가 **동일한 파이프라인** 통과:

```
1. [입력 수집]
   - CSV: 파일 업로드 → S3
   - API: AxHub fetch → 페이지네이션 처리

2. [정규화] (각 어댑터가 자체 포맷 → 공통 EmployeeImportRow 변환)

3. [검증] (공통 모듈 /modules/employee/bulk/validator.ts)
   - 필드 형식, 중복, 사번/이메일 충돌 등

4. [충돌 해결]
   - 수기 모드: status='awaiting_confirm' → HR이 UI에서 결정
   - API 모드: conflictStrategy 자동 적용

5. [실행] (트랜잭션, 라인별 BulkOperationRow 기록)
   - Appointment 트랜잭션 자동 생성 (시점 기반 이력 보장)

6. [완료] 
   - BulkOperation.status = 'completed'
   - 24h 롤백 가능 윈도우
   - 알림 발송 (시작자 + HR 관리자)
```

#### AxHub 연동 시 추가되는 흐름 (P2)

```
AxHub Webhook → /api/webhooks/axhub/employee-changed
  → BulkOperation(axhub_sync_employees) 생성
  → AxHubEmployeeDirectory.bulkSync() 호출
  → 공통 파이프라인 진입 (검증 → 충돌 해결 → 실행)
```

→ 자세한 인터페이스 명세는 `07_AxHub_연동.md` 에서 정의 (다음 작성).

### 1-7. AI 자연어 명령 (Claude Haiku)

**왜 Haiku**:
- 의도 분류 작업 = 단순. 저렴+빠름이 핵심
- 사용자가 ⌘K 누르고 자연어 입력 → 0.5초 안에 응답 필요

**처리 흐름**:
```
사용자 입력 → 시스템 프롬프트 (가능한 의도 목록 + 파라미터 스키마)
→ Claude Haiku 호출 → JSON 응답 (intent_type + parameters + confidence)
→ confidence 임계값 통과 시 자동 진입, 아니면 fallback 옵션 제시
```

**예시**:
```
입력: "내일 휴가 신청"
→ { intent: "create_leave_request", params: { date: "2026-05-20" }, confidence: 0.95 }
→ 휴가 신청 양식으로 이동 + 시작일 자동 채움
```

### 1-8. 검색 인프라 (pg_trgm + pg_bigm)

**왜 Elasticsearch 안 씀**:
- 운영 부담 (별도 클러스터)
- 우리 검색량 = 회사 단위. 수만 건 수준. Postgres로 충분
- AxHub 인프라 통합 시 단순함 우위

**`pg_trgm`**: 영문 + 한국어 음절 단위 트라이그램
**`pg_bigm`**: 한국어 형태소에 더 적합 (2-gram)

**둘 다 설치, 검색 대상에 따라 선택 사용**

**시드 SQL 예시** (마이그레이션):
```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS pg_bigm;

-- 직원 검색 인덱스
CREATE INDEX idx_employees_search
  ON employees USING gin (
    (name || ' ' || coalesce(email, '')) gin_trgm_ops
  );
```

## 3. 코딩 컨벤션 (CMD에게 강제)

### 3-1. 파일·디렉토리 명명
- 디렉토리: `kebab-case` (`leave-of-absence`)
- 파일: 비-React = `kebab-case`, React 컴포넌트 = `PascalCase.tsx`
- 페이지 = `page.tsx`, 레이아웃 = `layout.tsx` (Next 컨벤션)

### 3-2. 함수·변수
- 함수: `camelCase`
- 타입/인터페이스: `PascalCase`. 인터페이스 접두사 `I` **금지** (`Employee` not `IEmployee`)
- Enum: `PascalCase` 키 + `SCREAMING_SNAKE_CASE` 값 — 또는 const-assertion union 선호
- 상수: `SCREAMING_SNAKE_CASE`

### 3-3. 컴포넌트 작성
- **모든 컴포넌트는 함수형 + TypeScript**
- Props는 `type ComponentNameProps` 로 명시
- 한 파일 = 한 컴포넌트 (작은 sub 컴포넌트는 같은 파일 OK)
- **클라이언트 컴포넌트는 명시적 `"use client"`** 표시 — 기본은 서버 컴포넌트

### 3-4. 서버 액션 vs Route Handler
- **Server Action**: 폼 제출, mutation (CRUD)
- **Route Handler (/api)**: 외부 호출, Webhook, 파일 업로드, GET API
- Server Action 명명: `createEmployee`, `updateLeavePolicy` (동사+명사)

### 3-5. 에러 처리
- **never throw raw** — 항상 `Result<T, E>` 또는 명시적 도메인 에러
- 도메인 에러: `/packages/shared/errors`
- API 응답: `{ ok: true, data } | { ok: false, error: { code, message } }`

### 3-6. 권한 체크
- **모든 mutation 진입점 = 권한 체크 한 줄**
  ```ts
  await assertPermission(user, 'leave.policy.manage', { companyId })
  ```
- 컴포넌트 레벨에서 권한별 UI 분기 = `usePermission` 훅 사용

### 3-7. 시점 기반 쿼리
- "현재 시점"과 "특정 일자 시점" 구분
  ```ts
  getEmployeePositionAt(employeeId, date)  // 명시적
  getCurrentPosition(employeeId)            // = getEmployeePositionAt(id, new Date())
  ```

### 3-8. 컬러·스타일 (Flex 카피 방지)
- **그라데이션 클래스 금지** (`from-* to-*`)
- **컬러는 디자인 토큰만 사용** (`bg-primary`, `text-foreground`) — 임의의 `bg-green-500` 금지
- Tailwind 토큰은 디자인 시스템 문서에서 확정 (다음 단계)

## 7. Anti-Patterns (CMD가 절대 하면 안 되는 것)

1. ❌ **`UPDATE employees SET position=...`** — 항상 새 `PositionHistory` row 추가
2. ❌ **휴가 일수 하드코딩** — 모든 정책은 `LeavePolicy` 테이블에서
3. ❌ **권한 체크 없는 mutation** — 모든 진입점에 `assertPermission`
4. ❌ **`localStorage` 사용** — Next.js 환경에서 신뢰 X, 항상 서버 상태
5. ❌ **그라데이션 / 임의 컬러** — 디자인 토큰만
6. ❌ **`any` 타입** — 명시적 타입 또는 `unknown`
7. ❌ **단일 회사 가정 하드코딩** — 모든 쿼리에 `companyId` 필터
8. ❌ **Audit log 누락** — 도메인 mutation은 항상 `auditLog.record()`
9. ❌ **Flex UI 직접 카피** — 패턴은 차용, 시각·텍스트는 우리 것
10. ❌ **결재선 컴포넌트 중복 구현** — `RecipientPicker` 재사용
11. ❌ **벌크 처리 우회** — CSV 임포트라도 `BulkOperation` + `BulkOperationRow` 기록 거치기. 직접 `prisma.employee.createMany()` 호출 금지. 나중에 AxHub 연동 시 흐름이 분기됨.
12. ❌ **`sync_locked_fields` 우회 수정** — AxHub가 관리하는 필드는 수기 UI에서 차단해야 함. Server Action에서도 명시적 검증.
